# Program structure

Phase 4 of the [roadmap](roadmap.md): the rest of Blueprint's authoring concepts, so that a real program (classes, functions, events, async) can be built entirely in graphs and run from generated TypeScript, Python and C#. This document records the design decisions for each feature: the Unreal behavior copied, how it maps to each language, and how Simulate runs it. [semantics.md](semantics.md) gains the execution rules as each feature lands.

Each feature is implemented for every language pack at once, so C# comes first: once it generates today's graphs, every later feature is built and tested in four targets (TypeScript, JavaScript, Python, C#).

## C# language pack

- **Generated file:** `Name.vgraph.cs` next to the graph, one class per graph, in a namespace taken from the nearest `.csproj`'s `RootNamespace` (else its file name) plus the folders below it, as Visual Studio does. SDK-style projects compile every `.cs` file, so placement needs no registration (docs/output-placement.md).
- **Types:** `bool`, `int` (C# `int`, 32-bit, as Unreal's `int32`), `float` (C# `double`, as Unreal 5's float pins), `string`, arrays as `List<T>`, sets as `HashSet<T>`, maps as `Dictionary<K, V>`, `any` as `object?`. Nullable reference types are enabled.
- **Values print** with the same rules as everywhere else (semantics.md, "Values"), through a generated formatting helper, since C#'s `double.ToString()` differs from JavaScript's.
- **Run:** a project needs no setup. Run builds a small console project the extension owns (under the operating system's temporary folder) that includes the generated file and the project's own `.cs` files, then calls `Start()`. In a project with a `.csproj`, Run uses the project's references.
- **Your code as nodes:** public static methods of public classes, marked with `/// @blueprint` in their XML documentation comment (C# has no free functions; instance methods come with classes, below). A scanner in `src/core` reads them, as for TypeScript and Python.
- **Simulate** runs C# graphs' JavaScript snippets, as for Python; C# code runs through Run.

## Flow control

Unreal's standard macros, as built-in nodes with Unreal's pins:

| Node | Behavior |
|---|---|
| For Loop | Runs Loop Body for each Index from First Index to Last Index (both included), then Completed. |
| For Loop with Break | The same; running its Break input stops the loop after the current Loop Body. |
| While Loop | Runs Loop Body while Condition (read before each pass) is true, then Completed. |
| For Each Loop (with Break) | Loop Body for each Array Element and Array Index, then Completed. Arrives with containers. |
| Do Once | Runs Completed the first time; again only after Reset. Start Closed starts it closed. |
| Do N | Runs Exit, counting in Counter, the first N times; Reset starts over. |
| Gate | Exit runs Enter only while open; Open, Close and Toggle change it; Start Closed. |
| MultiGate | Each Enter runs the next output (Out 0, Out 1, …); Is Random and Loop as in Unreal; Reset. |
| Flip Flop | Alternates A and B, starting with A; Is A tells which ran. |
| Switch on Int / String | Runs the output whose case equals Selection, else Default. Cases are added on the node, like Sequence pins. |

- Exec wires still may not loop back; loops come only from loop nodes, as in Unreal.
- A node's remembered state (Do Once's closed flag, Gate's open flag, Do N's counter, Flip Flop's side, MultiGate's position) belongs to the object in event graphs and lasts across events. In a function it is local to each call, as Unreal's macros are inside functions.
- **Infinite loops:** Simulate stops a loop after 1,000,000 passes with an error, as Unreal's editor does. Generated code has no limit.
- Hold-key placement for the new nodes, as in Unreal: F For Each Loop, G Gate, M MultiGate, N Do N, O Do Once (D Delay arrives with latent actions).

## Containers

- Arrays, sets and maps get real values: defaults in Details, **Make Array**, **Make Set** and **Make Map** with add-pin buttons, and Unreal's array, set and map functions (Length, Get, Set Array Elem, Add, Add Unique, Insert, Remove Index, Remove Item, Find, Contains, Clear, Last Index, Is Valid Index, Keys, Values, Find (map), Add (map)…).
- **Wildcard pins** adopt the type of the first wire connected to them, as in Unreal, and drop it when all their wires are gone. The node resolver gives wildcard nodes their adopted type, so everything downstream (editor, compiler, Simulate) agrees.
- Containers are reference values, as in Unreal: getting an array variable and adding to it changes the variable. Printing a container shows compact JSON (semantics.md, "Values").
- Get on an index out of range is an error that stops the run (Unreal returns a default and logs; an error is easier to find and is what each target language does anyway).

## Functions

- A **function graph** has one entry node (exec out, plus an output pin per input) and any number of **Return Nodes** (exec in, plus an input pin per output), as in Unreal. The signature is edited in Details: inputs, outputs, pure, description, category, and local variables, with Unreal's metadata: Keywords (more words the action menu finds it by), Compact Node Title (drawn large, as operators are), Deprecated with a message (left out of the palette, and its nodes warn), and Advanced View on an input (folded under the node's arrow until opened, wired or set). Macros take the same metadata.
- Placing a function: drag it from My Blueprint, or pick it from the action menu (its category). The call node takes the function's name and pins; renaming the function or changing its signature updates every call node (wires on removed pins are dropped, as Refresh Node does).
- Reaching the end of a function without a Return Node returns the outputs' defaults. Recursion works.
- **Local variables** start at their default on every call.
- **Pure functions** have no exec pins on their call nodes and are called wherever their outputs are used (semantics.md, "Data flow"); their own graph still runs from entry to return.
- **Generated code:** a method per function. One output is the return value; several outputs return an object with a field per output (TypeScript), a tuple (Python) or a named tuple (C#).
- **Function libraries** (`kind: functionLibrary`) generate a module of free functions (TypeScript, JavaScript, Python) or a static class of static methods (C#, in the folder's namespace). Their functions appear in the palette of every graph in the library's languages (its own and any it is also generated for: [node-authoring.md](node-authoring.md), gap 1), under the function's category or else the library's name, and generated code imports them from the library's generated file in the graph's language, as it imports project functions. Each language pack decides the exported names (`libraryExports`): camelCase, snake_case or PascalCase, so the library and its callers agree. Simulate runs a library function from its `.vgraph` file (an open editor's unsaved text first); its nodes don't light up in the caller's editor.
- **Collapse to Function** (node menu) moves the selected nodes into a new function, with inputs and outputs for the wires that crossed the selection, and calls it in their place, as Unreal does. **Collapse to Function in Library…** does the same into a function library the graph's language can call, or a new one ([node-authoring.md](node-authoring.md), gap 10).

## Macros

- A **macro graph** has an **Inputs** and an **Outputs** tunnel node (they can't be deleted) with any number of exec and data pins: in Details, a macro pin's type can be **Exec** (several exec outputs are what makes macros useful, as Unreal's flow-control macros show). A macro without exec pins is pure. Macros have no Pure setting and no local variables.
- Using a macro: drag it from My Blueprint, or pick it from the action menu. Double-clicking an instance (or a function call) opens its graph, as in Unreal (and F12, Go to Definition, does too: see [node-authoring.md](node-authoring.md), gap 5).
- Macros are **expanded inline** where they are used, at compile time and in Simulate (src/core/macros.ts); there is no macro method in generated code. Each use is a separate copy, so state nodes inside a macro (Do Once…) are separate per use. Wires into an instance continue from the Inputs tunnel's matching pin; an input with no wire passes on the value typed on the instance (else the pin's default). Inner nodes get ids "instance/inner", and diagnostics, generated-code markers ("Macro: Node") and Simulate's events point at the instance.
- A macro's own wiring is checked in the macro graph, even when nothing uses it; problems that only show where it is used (it uses itself, directly or through other macros; a missing macro) are reported on the instance. A macro may not hold events, a Function Entry or Return Nodes.
- **Macro libraries** (`kind: macroLibrary`) generate no code. Their macros appear in the palette of graphs in the library's language, and are expanded where used, so nothing is imported. The library's node definitions embed each macro's graph (with the library's own macros already expanded), so compiling and Simulate need nothing else.
- **Collapse to Macro** (node menu), as Collapse to Function, except that execution may enter and leave the selection in several places: each becomes an exec pin of the macro.

## Structs and enums

- Two more `.vgraph` kinds, as Unreal's assets: **`structure`** (named fields with types and defaults, stored as the document's `variables`) and **`enumeration`** (named values, stored as `enumerators`). They have no graphs and open in a field or value list editor instead of the canvas. **New Graph** offers every kind under Unreal's names (Blueprint Class, Blueprint Function Library, Blueprint Macro Library, Structure, Enumeration).
- They are workspace types: `struct:<Name>` and `enum:<Name>` pin types refer to them by name (so a name means one type in a workspace, as an asset name does in Unreal), the type pickers list those in the graph's language, and generated code imports them from their own generated file. The workspace service (src/extension/graph-libraries.ts) turns each into node definitions that carry the type (src/core/user-types.ts), so the compiler, Simulate and the editor learn it from the node registry. A graph that uses a type its language can't (declared in another language's graph file, or not declared at all) gets a compile error, and Simulate stops with it; a second file declaring a name already taken gets a problem in the Problems panel ([multi-language.md](multi-language.md)). A struct or enum can be shared: its **Also generate for** languages get a generated file each, and their graphs use the one type.
- Nodes: **Make** and **Break** for each struct (pure), **Set members in** (its Details choose which fields get a pin; a struct wired from a variable's Get is written back to the variable, as Unreal's by-reference input), and for enums **Switch on** (an exec output per value), **==** and **!=**. Print and To String show an enum value's name. Unconnected enum pins pick a value from a dropdown; struct pins are fed by Make.
- Structs are values, as in Unreal: no node changes a struct in place (Set Members makes a new one and assigns it), so copies never affect each other. Generated as a class with readonly fields in TypeScript and JavaScript, a frozen dataclass in Python, and a `readonly record struct` in C#. Enums are generated as an object of name strings (`as const`, with a matching type) in TypeScript, a frozen object in JavaScript, an `Enum` in Python and an `enum` in C# (values whose name isn't a valid member name carry it as `[Description]`). TypeScript output avoids `enum` and parameter properties so Node.js can run it by stripping types.
- Stored values: an enum value is stored by its value's id, so renaming a value keeps graphs working; a struct variable's default is its structure's field defaults.
- **Split struct pins:** right-click a struct pin for **Split Struct Pin**; it becomes a pin per field ("Start X", "Start Y"), and a field that is a struct can be split again. **Recombine Struct Pin** (on any of the field pins) brings the struct pin back. Splitting or recombining drops the wires of the pins that go, as Unreal does. The node stores the split pins in `properties.split`; before compiling and Simulate each split becomes a hidden Make or Break node (ids "node/split:pin"), so generated code is what wiring Make or Break by hand would give.
- Not yet: sets and map keys of structs or enums (their order and hashing differ between languages; a compile error says so). A container inside a struct is shared by copies of the struct, as containers are shared everywhere (semantics.md, "Containers").

## Custom events and event dispatchers

- **Custom Event** nodes (event graphs only) take a free name when placed (CustomEvent, CustomEvent_1…); their name and inputs are edited in Details, stored on the node (`properties.name`, `properties.inputs`). Each custom event can be called from the action menu (a Call node, titled with the event's name, in any graph of the class); renaming the event renames its Call nodes. Functions, custom events and dispatchers share one set of names, as in Unreal.
- Calling a custom event runs it right away, as Unreal does for events called directly. In generated code each custom event is a method (lowered as an event function, src/core/compiler/lower.ts); inside its own flow its inputs are the method's parameters, and inputs read from other flows are kept in fields when it runs, as Unreal keeps an event node's outputs.
- **Event Dispatchers** are declared in My Blueprint's Event Dispatchers section with inputs (edited in Details). Dragging one onto a graph offers Unreal's choices: **Call** (runs every bound event), **Bind** (Bind Event to), **Unbind** (Unbind Event from), **Unbind all** (Unbind all Events from), and, in event graphs, **Assign** (a Bind node and a new custom event with the dispatcher's inputs, wired together). The action menu offers the same nodes. Deleting a dispatcher deletes the nodes that use it.
- The red pin on a Custom Event stands for the event (type `delegate:(<input types>)`); it connects to Bind's and Unbind's Event pin when the event's inputs match the dispatcher's. Changing an event's or dispatcher's inputs drops the wires that no longer fit.
- Bound events run in the order they were bound. Binding the same event twice binds it once; events bound or unbound while a Call runs take effect from the next Call.
- Generated as a small `EventDispatcher` helper in each file that declares one: TypeScript and JavaScript keep (object, method) pairs, Python keeps bound methods, C# keeps `Action<…>` delegates in a list (each compares equal for the same object and method, so Unbind and binding twice work, and step 9's binding of other objects' events needs nothing new).

## Classes

- Every `kind: class` graph is a class: its variables, functions, custom events and dispatchers are members; Start is its constructor-time entry (`start()`).
- **Object references:** `object:<Class>` pins; every class graph in the workspace is a type in the type pickers. **Construct <Class>** (Unreal's "Construct Object from Class") creates an object and runs its Start events, as spawning runs BeginPlay; **Self** is the object the graph belongs to; **Is Valid** tells a set reference from an empty one. Implemented in src/core/objects.ts: a class's public members travel on its Construct node's definition, registered by the workspace service, so the compiler, Simulate and the editor learn them from the node registry.
- Member nodes on another object (Get, Set, function calls, custom events, and Call/Bind/Unbind/Unbind all of an event dispatcher) carry `properties.class` and a **Target** pin; the action menu lists each workspace class's members under its name. An unconnected Target is Self for the class's own members and an error otherwise. An empty Target stops the run ("Accessed None", as in Unreal). Events bound to another object's dispatcher are the binding object's own custom events.
- Generated code names a class's public members through one shared function per language (src/core/compiler/names.ts), so a class's own file and every file that uses it agree. Classes import each other: TypeScript and ES modules import at the top; CommonJS and Python import classes at the end of the module, after the class is defined, so two classes that use each other both load. Printing an object is a compile error (Unreal needs Get Display Name, which comes later); Simulate prints its class name.
- **Target pins:** calling a function, getting or setting a variable, binding a dispatcher or calling a custom event on another object uses the node's Target pin, as in Unreal; unconnected Target means Self.
- **Inheritance:** a class graph may extend another class graph, chosen as Parent Class in **Class Settings** (Details for an event graph with nothing selected; stored as `parent`). Its parent's variables, functions, custom events and dispatchers are its own: the action menu offers them and their Target defaults to Self, and a subclass object wires where its parent class is expected. Functions are virtual, as in Unreal: My Blueprint's **Override** menu makes a function with a parent function's name and signature, wired to **Parent: <Function>**; calls of that function, the parent's own included, run the override. A subclass without Start nodes keeps its parent's Start; one with Start nodes replaces it and can call **Parent: Start**. A subclass may not reuse its ancestors' variable, event or dispatcher names, and an override must keep the signature. Generated code uses the language's inheritance (`extends`, `class B(A)`, `: A` with `virtual`/`override`); a subclass's internal fields carry its name so they can't meet its parent's private ones. Simulate runs an object of a subclass as a chain of its classes, each with its own variables. Classes from the project's code as parents come later (Phase 3's deferral stands).
- **Interfaces:** an `interface` `.vgraph` kind (New Graph's **Blueprint Interface**) declares functions by their signatures. A class adds interfaces under Implemented Interfaces in Class Settings (stored as `interfaces`), and My Blueprint's Override menu offers each interface function to implement; one it doesn't implement does nothing and returns defaults, as in Unreal. `interface:<Name>` pins take objects of classes that implement it (or whose ancestors do), and the action menu offers each interface function as a call with a Target of that type. Generated code: a C# `interface`, a Python class the implementing classes inherit from, and in TypeScript an `interface` type plus a `Symbol.for` tag the implementing classes carry, which an `is<Name>` guard checks (TypeScript's interfaces don't exist at run time); JavaScript gets the tag and guard.
- **Cast To** a class or interface (every workspace class and interface has one) has Cast Succeeded and Cast Failed exec outputs and the object as that type, as in Unreal. Generated as `instanceof` (the interface's guard in TypeScript and JavaScript), `isinstance`, and C#'s `is`. The pure version comes later.
- **Visibility:** a class's variables and functions have an Access setting in Details (Unreal's Private flag and Access Specifier): Public (the default), Protected (the class and its subclasses) or Private (the class alone), stored as `access`. Using a member from where it isn't visible is a compile error, and the action menu only offers the members a class may use. Generated code spells it as `private`/`protected` in TypeScript and C# (a private C# method isn't virtual), and as a leading underscore in Python; JavaScript has no keyword.

## Latent actions

- **Delay** (Duration in seconds) and **Retriggerable Delay** (src/core/latent.ts), with Unreal's rules: a latent node suspends only the chain after it, so the node returns at once (a Sequence's next output runs) and Completed runs when the time is up; while a Delay is waiting, running it again does nothing; a Retriggerable Delay starts its countdown over. Hold D and click to place a Delay. Async functions from the project's code are latent nodes too ([code-as-nodes.md](code-as-nodes.md), "Async functions"), and more (Delay Until Next Tick) follow the same model. A latent node has a clock in its title.
- As in Unreal, latent nodes belong in event graphs (and macros used there), not in functions: a function runs to its end at once (a compile error says so). A Delay whose Completed leads back to it is a timer, not an exec loop.
- The chain after Completed reads an event's inputs as they are when it runs (their latest values), as Unreal reads an event node's outputs.
- **Generated code:** Completed is a callback, not an `await`, so every language keeps Unreal's order without async methods: TypeScript and JavaScript use `setTimeout` (Node.js runs timers in the order they fall due and waits for them before exiting); Python and C# put latent actions of every class on one queue per process (kept in `sys.modules` and the AppDomain), which runs them in due order once `start()`/`Start()` returns: Run does that, as does the Python module's `__main__` block; C# programs call any generated class's `RunLatentActions()`.
- **Simulate** runs latent actions on a virtual clock: a Delay doesn't wait in real time, and pending actions run in order of their due time (ties in the order they were started). Generated code waits in real time, which gives the same order when the times differ; graphs that rely on two Delays of the same length finishing in a particular order are not portable. Simulate stops after 10,000 latent actions, as a timer that keeps starting itself runs forever.

## Entry points and framework packs

- **Main** is the program's entry point: an event with the command-line arguments (Args, an array of strings). Run calls it after Start with the `blueprintVisualScripting.runArguments` setting; Simulate passes the same arguments. Generated code gives it a method (`main`, `main`, `Main`); a Python module's `__main__` block calls it with `sys.argv[1:]`, and other programs call it themselves. A class has one Main.
- **Framework packs** add events a framework runs, as node libraries (`*.node.json`): an event definition has the implementation `{ "kind": "event", "method": "<Name>" }`, its data outputs are the event's parameters, and generated code gives each class that uses it a public method named after `method` in the language's style (`onCommand`, `on_command`, `OnCommand`), which the framework's host code calls. Like Start and Main, these events belong in event graphs. Simulate can't run a framework's events (nothing calls them). The example pack in sample/visual-nodes/CLI has an On Command event.
- **Test Case** events came with Phase 5: see [debugging.md](debugging.md), "Test Case".
